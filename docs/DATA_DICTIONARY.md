# Data Dictionary

All tables are generated by `sop_planning.datagen` (seeded, reproducible)
and written to `data/raw/*.csv`. Dates: `2024-01-01` to `2025-12-31`
(2 full years, so both a Nowruz and a Yalda cycle appear twice).

## Dimensions

| table | grain | key columns |
|---|---|---|
| `dim_employee` | 1 row per employee (~200) | `employee_id`, `role`, `department`, `production_line_id`, `shift`, `employment_type`, `hire_date`, `monthly_wage_irr` |
| `dim_production_line` | 1 row per line (5) | `line_id`, `line_name`, `capacity_units_per_hour`, `shifts_per_day`, `changeover_minutes`, `commissioned_date` |
| `dim_product` | 1 row per SKU (25) | `product_id`, `product_name`, `category`, `primary_line_id`, `unit_weight_g`, `shelf_life_days`, `unit_price_irr`, `is_seasonal`, `seasonal_peak` |
| `dim_supplier` | 1 row per supplier (8) | `supplier_id`, `supplier_name`, `material_categories`, `avg_lead_time_days`, `reliability_score`, `payment_terms_days` |
| `dim_raw_material` | 1 row per material (18) | `material_id`, `material_name`, `unit_of_measure`, `unit_cost_irr`, `default_supplier_id`, `lead_time_days`, `safety_stock_days` |
| `dim_region` | 1 row per sales region (7) | `region_id`, `region_name`, `customer_type`, `payment_terms_days` |
| `bom` | 1 row per (product, material) | `product_id`, `material_id`, `qty_per_unit` |

## Facts

| table | grain | key columns |
|---|---|---|
| `fact_sales_history` | 1 row per (date, product, region) with sales > 0 | `date`, `product_id`, `region_id`, `units_sold`, `unit_price_irr`, `revenue_irr`, `is_promo_day` |
| `fact_production_log` | 1 row per (date, line, product) produced | `date`, `line_id`, `product_id`, `planned_units`, `produced_units`, `scrap_units`, `downtime_minutes` |
| `fact_inventory_transactions` | 1 row per (date, material) event | `date`, `material_id`, `transaction_type` (`Consumption` / `Receipt` / `OnHandSnapshot`), `quantity` |
| `fact_purchase_orders` | 1 row per PO | `po_id`, `material_id`, `supplier_id`, `order_date`, `expected_delivery_date`, `actual_delivery_date`, `quantity`, `unit_cost_irr`, `status` |
| `fact_workforce_availability` | 1 row per (date, line, shift) | `date`, `line_id`, `shift`, `scheduled_headcount`, `present_headcount` |

## Pipeline outputs

Written to `data/processed/planning_warehouse.db` (SQLite) and mirrored as
Parquet in `data/processed/planning_output_parquet/`:

| table | grain | key columns |
|---|---|---|
| `fact_demand_forecast` | 1 row per (product, forecast week) | `product_id`, `week_start`, `forecast_units` |
| `fact_production_plan` | 1 row per (line, product, week) | `line_id`, `product_id`, `week_start`, `forecast_units`, `allocated_units`, `unmet_units` |
| `fact_material_requirements` | 1 row per (material, week) | `week_start`, `material_id`, `required_quantity`, `projected_on_hand_start`, `projected_on_hand_end`, `below_safety_stock`, `recommended_order_qty` |
| `fact_sop_weekly_summary` | 1 row per week | `week_start`, `forecast_units`, `allocated_units`, `unmet_units`, `fill_rate`, `revenue_captured_irr`, `revenue_lost_irr`, `materials_below_safety_stock` |
| `fact_forecast_accuracy` | 1 row per product + 1 overall row | `product_id`, `mape`, `wape`, `n_weeks` |
| `fact_working_capital` | 1 row per week (steady-state weeks only — see below) | `week_start`, `dio`, `dso`, `dpo`, `ccc` |

## Seasonality reference

| `seasonal_peak` value | products | pattern |
|---|---|---|
| `Nowruz` | most Kolucheh varieties, Nowruz Sweets Box | ~18-day pre-holiday build-up peaking at Nowruz, then a sharp drop |
| `Yalda` | Rosewater Kolucheh, Yalda Night Gift Box | ~10-day symmetric bump around Yalda (Dec 21) |
| `Ramadan` | Ramadan Date & Nut Pack | elevated demand across the (approximate) Ramadan window |
| `Summer` | Summer Fruit Roll Cake | elevated June–August |
| `AutumnStart` | Back-to-School Snack Pack | elevated mid-September–early October (Iranian school year start) |
| `None` | everyday items (sponge cakes, wafers, plain cookies) | weekday/weekend pattern + slow trend only |

## Cash Conversion Cycle (`fact_working_capital`)

`CCC = DIO + DSO - DPO`, each a trailing-90-day average, computed weekly:

- **DIO** (Days Inventory Outstanding): from the real simulated raw-material
  inventory ledger — `(average on-hand value / trailing consumption value) × 90`.
  Finished-goods inventory is not included: these products have short
  shelf lives (see `dim_product.shelf_life_days`) and are made close to
  when they're sold, so DIO here is entirely raw-material-driven.
- **DSO** (Days Sales Outstanding): from a simulated accounts-receivable
  ledger — each day's revenue is "invoiced" and collected
  `dim_region.payment_terms_days` later (± a little jitter), then
  `(average AR balance / trailing revenue) × 90`.
- **DPO** (Days Payable Outstanding): the same construction on the supplier
  side, using `dim_supplier.payment_terms_days` against purchase order
  value at delivery.

The first ~7 months of the 2-year window are excluded from
`fact_working_capital`: the receivables/payables ledgers start at a zero
balance and need a full payment-term cycle (up to the 120-day export term)
plus the 90-day trailing window before they reach a realistic steady state.
Reporting through that ramp-up would show an artificially improving trend
that's really just the ledger filling up, not a business change.
